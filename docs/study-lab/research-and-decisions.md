# Research and implementation decisions

## Recommendation

Prototype a narrow evidence-auditable technical study workflow. Do not build a
generic “upload and chat” competitor from scratch or market a second model as
a correctness guarantee. Source ingestion, bounded context, transparent review
and independently attempted practice are the useful hypotheses to evaluate.

## Why OpenTutor

We inspected OpenTutor at `a890519` and Open Notebook at `a0f6f30` before choosing
the foundation. Both repositories have MIT code licenses. OpenTutor already
provides a Next.js learning UI, FastAPI, local SQLite, course uploads, quizzes,
flashcards, FSRS review and Ollama/provider integrations. It is closer to the
proposed study workflow. Open Notebook is a broader research-notebook platform
with SurrealDB and worker infrastructure; implementing the learning interface
there would require more new product work.

This is a fit judgment, not a claim that OpenTutor is more reliable or mature.
Some advertised OpenTutor learning/knowledge-graph capabilities are experimental
or disabled by default. We found baseline TypeScript and ingestion-test issues
and isolated their fixes in separate branches.

| Alternative | Documented overlap | Remaining opportunity to test |
|---|---|---|
| NotebookLM / Gemini Notebook | Source-based study, learning guidance, flashcards/quizzes | Inspectable local context and reviewer configuration |
| ChatGPT Study Mode | Guided questioning, explanations and checks | Explicit course-scoped context policy and self-hosting |
| StudyFetch / RemNote | Uploaded materials and structured learning/review | A narrower technical-study workflow with measurable evidence review |
| Open Notebook | Self-hosting, sources and model choice | More learning-specific interface work than OpenTutor |
| OpenTutor baseline | Tutor, practice, uploads and local models | Bounded independent review, explicit packet audit, page-aware evidence |

This is a documentation comparison, not hands-on competitor benchmarking. We
have not measured competitors' internal verification, costs or learning outcomes.

## What the PDF experiment actually showed

The preceding experiment (18 October 2026) downloaded three versioned research
PDFs: Attention Is All You Need v7, MiniCheck v2 and Lost in the Middle v3, with
63 physical pages total. The separately saved experiment report and reproduction
ZIP contain the original hashes, versions and measurements. They are not
regenerated by the app's current parser.

| Text representation | Total o200k_base tokens |
|---|---:|
| pypdf | 63,036 |
| MarkItDown | 109,633 |
| PyMuPDF4LLM | 63,419 |

Markdown did not inherently compress this sample: MarkItDown increased tokens
by 73.9%, PyMuPDF4LLM by 0.6%. These parsers also extracted different content;
this is not a controlled punctuation-only experiment. A visual spot check found
an attention equation missing from one text-only Markdown output. Original page
images matter even when the extracted prose looks plausible.

Across 12 manually authored questions, resending only the relevant full
document contributed 229,433 prompt-body tokens. Top-4 BM25 tutor packets used
20,749; tutor-plus-reviewer packets used 41,910. These are encoding counts, not
API bills. Outputs, caching, wrappers, retries, ingestion and local compute were
excluded. Candidate answers were manually composed, not generated live.
Retrieval supplied the demonstrated context reduction; the reviewer added about
102% to the retrieval tutor's input volume. This establishes no saving over
NotebookLM or another product that already retrieves/caches context.

A real local quantized generic NLI classifier was also tested on 36 hand-written
claims. It falsely approved a technical claim allowing decoder attention to
future tokens with a score around 0.964. This small diagnostic is neither a
MiniCheck evaluation nor an accuracy benchmark for the implemented generative
reviewer. It explains why this UI exposes uncertainty instead of a “verified
correct” badge.

## How those results shaped the prototype

- Parse native PDF text cheaply, preserve physical page numbers, and flag sparse
  text and visual objects. Keep originals in OpenTutor's existing upload store.
  These flags are heuristics, not calibrated quality scores; vector diagrams and
  layout errors can escape them. Uploaded PDFs should be checked visually.
- Treat Docling/Marker/OCR as candidates for a later structured-parser adapter,
  not as automatic fidelity improvements. Benchmark equation/table retention
  and runtime before enabling model downloads or OCR for every upload.
- Budget serialized evidence, including source metadata and JSON overhead.
  Retain whole recent messages, explicitly report omissions, and do not load
  personal biography or cross-course memory in the Study Lab route.
- Keep the latest question, goal, complete latest answer, immediately relevant
  assistant task and evidence for review. Reviewing an answer without its
  question/evidence is not sufficient verification. Oversized packets skip
  review explicitly rather than silently dropping part of an answer.
- Validate exact quotations and citation IDs deterministically. The model still
  judges whether the quote supports the claim. Completeness is not certified.
- Use predict-first numerical exercises and recall/practice prompts. Do not
  categorize learners by fixed “visual/auditory learning styles.” Preferences
  are useful inputs; learning gains need measurement.

## Next evaluation gate

Build a held-out set of 100–200 questions with independently annotated evidence
spans. Include missing evidence, misleading citations, diagram-dependent
questions, mathematical mistakes, ambiguous follow-ups and genuine tutor errors.
Compare the same retrieval tutor with and without review. Report false approvals,
false rejections, claim coverage, invalid JSON, latency and total costs. Then test
delayed unaided recall/transfer with learners before claiming learning benefits.
